# WPGraphQL and headless sites

Activate WPGraphQL alongside Better Schema Markup. WPGraphQL is optional in production; WordPress JSON-LD output works without it. Local `vp run start` installs both plugins. The integration uses WPGraphQL's [interface fields](https://www.wpgraphql.com/docs/interfaces) and [field resolvers](https://www.wpgraphql.com/docs/graphql-resolvers).

Query posts, pages, or custom post types exposed by WPGraphQL through `ContentNode`:

```graphql
query Schema($id: ID!) {
  contentNode(id: $id, idType: DATABASE_ID) {
    betterSchema {
      raw
    }
    betterSchemaType
  }
}
```

`raw` is a JSON string containing the same complete graph as WordPress output, including WebSite and publisher identity. `betterSchemaType` is the effective per-post choice (including configured defaults): `Article`, `BlogPosting`, `WebPage`, or `none`. With `none`, `betterSchema` is null. WPGraphQL controls node visibility; the schema resolver also prevents public access to draft, private, and password-protected post data. Editors with permission to edit the post can query its schema.

For site-level data, use `{ betterSchema { raw } }` at the root. It includes WebSite and Organization/Person, without a WebPage. Developer piece and graph filters still apply, using context type `site`. Avoid rendering the root graph alongside a content graph: the content graph already includes those entities.

## Frontend URL

In Settings → Better Schema, set **Frontend URL**, for example `https://www.example.com`. Leave it empty for ordinary WordPress sites. Only absolute HTTP(S) bases without credentials, queries, or fragments are accepted. A path prefix such as `https://example.com/blog` is supported.

The shared builder replaces the WordPress home/site base in schema URL properties and references, preserving paths, queries, and fragments. The more specific WordPress base wins when WordPress is installed in a subdirectory. This affects GraphQL, previews, and WordPress HTML output. External URLs and plain text are preserved. Local media URLs are also mapped: ensure your frontend serves/proxies these paths, or use external media/CDN URLs. This does not change WordPress permalinks or the GraphQL endpoint, and does not translate custom frontend route structures.

## Next.js App Router example

This server component accepts the WordPress database ID from your route/data layer. Configure `WORDPRESS_GRAPHQL_URL` on the server with the WordPress GraphQL endpoint. The example requests public content without authentication.

```tsx
import { notFound } from "next/navigation";

type SchemaResponse = {
  data?: {
    contentNode: { betterSchema: { raw: string | null } | null } | null;
  };
  errors?: readonly { message: string }[];
};

export async function ArticleSchema({ postId }: { postId: number }) {
  const endpoint = process.env.WORDPRESS_GRAPHQL_URL;
  if (!endpoint) throw new Error("WORDPRESS_GRAPHQL_URL is required");
  const response = await fetch(endpoint, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      query: `query Schema($id: ID!) {
        contentNode(id: $id, idType: DATABASE_ID) {
          betterSchema { raw }
        }
      }`,
      variables: { id: String(postId) },
    }),
    cache: "no-store",
  });
  if (!response.ok) throw new Error("Schema request failed");
  const result: SchemaResponse = await response.json();
  if (result.errors?.length || !result.data) throw new Error("Schema query failed");
  if (!result.data.contentNode) notFound();
  const raw = result.data.contentNode.betterSchema?.raw;
  if (!raw) return null;
  return (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: raw.replace(/</g, "\\u003c") }}
    />
  );
}
```

Render this once on the matching content page. Do not JSON-stringify `raw` again: it is already serialized JSON. Escaping `<` keeps user-authored text from closing the script tag, following the [Next.js JSON-LD guidance](https://nextjs.org/docs/app/guides/json-ld). If you add caching, invalidate it when posts or site schema settings change.

## Moving from wp-graphql-yoast-seo

Replace `seo { schema { raw } }` with `betterSchema { raw }`, and read `node.betterSchema?.raw` instead of `node.seo.schema.raw`. The graph is generated by Better Schema Markup; it is not an alias of Yoast's graph. Remove the old schema script from your frontend to avoid duplicate entities. Other SEO fields can continue to come from your SEO integration. Configure site identity, schema defaults, and frontend URL in Better Schema settings.

## Tests

`vp run start` installs WPGraphQL into both local environments. `vp run test` runs real GraphQL integration queries. The PHPUnit bootstrap loads WPGraphQL from the sibling plugin directory; non-wp-env runners can set `WPGRAPHQL_PLUGIN_FILE` to its main PHP file. CI downloads WPGraphQL before running PHPUnit.
